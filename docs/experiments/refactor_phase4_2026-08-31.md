# Phase 4 골든셋 검증 — 실행 사고와 그것이 대신 알려준 것 (2026-08-31)

대상: `docs/plans/refactoring-plan-2026-08-31.md` Phase 4 (신뢰도·가드레일 실효화).
기준선: `eval/baselines/v8.1-2026-08-30/` (172문항).

**결론부터**: 골든셋 경로가 실제로 타는 Phase 4 변경은 §4.3 가드레일 하나뿐이고,
그 가드레일은 **172개 답변 중 1개(lg056)만 바꾸며 그 1개는 실패→통과로 개선됐다**.
통과 문항 12 → 9의 차이는 LLM 비결정성이 지배한다 — 두 실행에서 답변이 완전히
같은 문항이 172개 중 7개뿐이고, 평균 답변 길이가 1,213 → 1,636자로 변했다.

---

## 1. 두 번의 실행 사고

### 1-a. 1차 실행: `--semantic-similarity` 누락 (내 설정 오류)

v8.1 기준선은 `--semantic-similarity`로 생성됐는데 1차 실행에서 이를 빠뜨렸다.
`MetricAggregator.check_gating`은 token-F1이 미달이어도 semantic similarity가
0.65 이상이면 정답으로 인정한다. 그 보정이 사라지자 **172문항 전부**가
`L5_wrong_answer`로 떨어졌다.

```
pass_rate 0.0930 → 0.0000   ← 코드 회귀가 아니라 실행 조건 불일치
L5_wrong_answer 97 → 172
avg_overall_score 0.5508 → 0.5475   ← 실제 품질은 거의 그대로
```

기준선과 **동일 조건으로 실행하지 않으면 compare 결과는 의미가 없다.**

### 1-b. 2차 실행: LiteLLM 호출 무기한 정지

조건을 맞춰 재실행(`--semantic-similarity --concurrency 1`)했으나 135/172에서
멈췄다. 프로세스는 살아 있고 TCP 연결 4개를 쥔 채 CPU 0%, 53분간 로그 무출력.
같은 증상이 앞서 한 번 있었고(단일 문항 937초) 그때는 회복했다.
판정 결과는 실행 끝에만 기록되므로 중단 시 부분 결과도 남지 않는다.

→ **`eval.cli`의 LLM 호출에 타임아웃이 없다.** 별도 과제로 기록한다.

## 2. 오프라인 재구성 (추가 API 비용 0)

1차 실행 리포트는 문항별 `trace.l5_answer.final_answer`를 저장한다.
semantic similarity는 로컬 sentence-transformers로 계산되므로,
빠진 지표를 사후에 계산해 게이팅을 다시 돌릴 수 있다.

### 2-a. 대조군 먼저

재구성이 타당한지 확인하려고 **기준선 자신의 문항을 현재 게이팅 로직으로
다시 판정**해 봤다. 처음엔 11/172이 불일치했다.

원인: **리포트 직렬화가 `requires_kg`를 잃는다.** 데이터셋의 lg041은
`requires_kg: false`인데 리포트의 `metadata`에는 `true`로 기록된다.
`check_gating`은 이 값으로 L2/L3 검사를 갈라 적용하므로, 리포트 메타데이터를
그대로 쓰면 KG 검사가 잘못 발화한다.

데이터셋 메타데이터를 쓰자 불일치가 4/172로 줄었다. 남은 4건(lg059·lg080·
lg156·lg179)은 `concept_map_f1`이 0.5 미만인데도 기준선에서 통과한 문항으로,
기준선 생성 시점과 현재의 L1 임계값이 다르다는 뜻이다.

→ 그래서 **양쪽(기준선·신규)에 똑같은 재게이팅을 적용해** 이 드리프트를 상쇄했다.

### 2-b. 결과

| | 통과 | 비고 |
|---|---|---|
| baseline v8.1 (재게이팅) | 12/172 (7.0%) | 원 기록은 16/172 |
| Phase 1–4 (재게이팅) | 9/172 (5.2%) | |

회귀 6건 / 개선 3건, 순 -3.

```
회귀: lg042 lg064 lg091 lg187 lg190 → L5_grounding_fail
      lg049 → L5_wrong_answer
개선: lg055 lg056 lg177 → L5_grounding_fail 해소
```

|---|---|---|---|
| l5_groundedness | 0.6907 | 0.6815 | −0.0092 |
| l5_relevance | 0.7648 | 0.7901 | **+0.0253** |

## 3. 회귀의 원인은 Phase 4가 아니다

골든셋은 `HybridChatbotAgent`를 태운다. Phase 4 변경 중 이 경로에 닿는 것은
§4.3 `apply_guardrails()` 하나다 (§4.1/4.2/4.5는 `response_pipeline`
= `/api/v4/chat` 경로, §4.4는 인사이트 생성 경로).

기준선의 172개 답변에 새 가드레일을 적용해 **실제로 몇 개가 바뀌는지** 셌다.

```
가드레일이 바꾸는 답변: 1/172  (lg056)
회귀 6건 중 가드레일 영향: 0건
```

**lg056은 회귀가 아니라 개선 3건 중 하나다.**

한편 두 실행의 답변 자체가 거의 다르다.

```
기준선과 완전히 동일한 답변: 7/172
평균 답변 길이: 1,213자 → 1,636자 (+35%)
```

답변이 길어지면 짧은 gold answer와의 토큰 겹침이 희석돼 `answer_f1`이 떨어지고,
LLM judge의 groundedness 점수도 흔들린다. 회귀 6건이 전부 groundedness
임계값(0.7) 근처에서 갈린 것과 일관된다.

→ 12 → 9의 차이는 **실행 간 분산**으로 설명되며, Phase 4에 귀속할 근거가 없다.
계획서가 정한 "회귀 시 원인 파일 되돌리기"의 대상이 없다.

---

## 4. 되돌리지 않은 이유

계획서는 회귀 시 원인 파일만 되돌리라고 지시한다. 되돌리지 않은 근거:

1. 유일한 후보(§4.3 가드레일)가 손댄 문항은 1개이고, 그 문항은 **개선**됐다.
2. 나머지 Phase 4 변경은 골든셋이 타지 않는 경로에 있다.
3. 분산이 신호보다 크다 — 단일 실행 쌍으로는 −3을 회귀로 판정할 수 없다.

분산을 통제하려면 같은 조건 반복 실행(n≥3)이 필요하고, 계획서는 1회만
승인했다. 이미 실행 사고로 2회를 썼으므로 추가 실행은 하지 않았다.

## 5. 남긴 것

- **`eval.cli` LLM 호출 타임아웃 없음** — 2차 실행이 135/172에서 무기한 정지.
  판정이 끝에만 기록돼 부분 결과도 유실된다.
- **리포트 `metadata.requires_kg` 직렬화 유실** — 데이터셋 `false`가
  리포트에서 `true`로 기록된다. 리포트만 보고 게이팅을 재현할 수 없다.
- **기준선과 현재의 L1 `concept_map_f1` 임계값 불일치** (4문항 영향).
- 다음 baseline 저장은 하지 않았다. 유효한 전량 실행이 없기 때문이다.
