# 개선 사이클 4 — 채점 크래시·엣지 지표 설계·엔티티 커버리지 (2026-08-30)

대상 작업 패키지: P1(L3 엣지 재진단) + P2(L1 엔티티 커버리지) + P4 일부.
기준선: `eval/baselines/v4.1-2026-08-30/` → 신규 `eval/baselines/v5.0-2026-08-30/`.

---

## 1. 진단 (무비용 — v4.1 리포트 로컬 분석)

### 1-a. 채점 크래시로 7문항이 통째로 0점이었다 (측정 인프라 결함)

v4.1 리포트에서 트레이스가 완전히 빈 7문항을 발견했다. `trace.error`는
`cannot use 'dict' as a set element (unhashable type: 'dict')`.

원인: 골든셋 스키마 `GoldEvidence.constraints`는 `list[str | dict]`을 허용하는데,
`eval/metrics/l1_query.py`의 `set(gold.constraints)`가 dict를 그대로 집합에 넣어
**해당 문항의 채점 파이프라인 전체가 예외로 중단**됐다. 러너는 이를 잡아
zeroed metrics + 빈 응답으로 기록했으므로, 응답은 정상 생성됐음에도 L1~L5 전부
0점이고 judge 채점 자체가 수행되지 않았다.

- 영향 문항: dict constraint를 가진 정확히 7문항 (lg075, lg175, lg176, lg178,
  lg181, lg182, lg186) = 전체의 4.4%
- 그중 6문항이 `time` 도메인 — time 15문항 중 40%. **v1.0~v4.1에서 time이 최약
  도메인(0.265)이었던 것의 상당 부분이 시스템 품질이 아니라 이 크래시였다.**

### 1-b. L3 KG Edge F1은 이 데이터셋에서 판별력이 없다 (지표 설계 결함)

v4.1 문항별 gold `kg_edges` vs trace `kg_edges_found` 대조 결과:

| 항목 | 수치 |
|---|---|
| 골드 엣지가 있는 문항 | 105 / 160 (문항당 1~3개, 중앙값 1) |
| 골드 엣지가 없는 문항 | 55 (그중 23문항은 시스템이 엣지를 내서 F1=0.0) |
| 방출 엣지 수 (골드 있는 문항) | 평균 8.5개, 중앙값 10 (상한 12) |
| 평균 recall | 0.286 |
| 평균 precision | 0.031 |
| recall=1.0인 문항 | 26 / 105 |

규모 비대칭이 지배적이다. 골드 1개 · 방출 10개일 때 **완벽 회수의 F1은 0.18**이고,
F1 0.5 게이트는 총 방출 엣지가 3개 이하일 때만 도달 가능하다. requires_kg 130문항
중 125문항이 fail이었던 것은 시스템이 아니라 게이트가 상시 참이었기 때문이다.

### 1-c. 골드 엣지의 46%는 KG에 존재하지 않는다 (측정 상한)

골드 엣지 언급 164건을 현재 KG(2,700 트리플) + 제품 슬러그 파생 엣지와 대조:

| 구분 | 건수 |
|---|---|
| KG에 그대로 존재 | 47 |
| 제품명 슬러그로 파생 가능 | 42 |
| **KG에 존재하지 않음** | **75 (45.7%)** |

미존재 예: `tirtir -rankedIn-> face_powder`(9건), `laneige -competesWith-> cosrx`(4건),
`laneige -hasProduct-> water_bank`(6건). 골드는 도메인 지식으로 작성됐고 실제 크롤
스냅샷에는 해당 사실이 없다(LANEIGE는 lip_care·lip_makeup·face_powder에만 랭크인,
competesWith는 카테고리 동시 등장으로 산출되어 blistex·chapstick 등이 나온다).

**따라서 엣지 recall의 구조적 상한은 약 0.54다.** 골드를 시스템 출력에 맞춰
고쳐 쓰는 것은 게이밍이므로 하지 않았고, 상한을 명시하는 쪽을 택했다.

### 1-d. 잔여 미스의 원인 유형 (도달 가능한 것만)

| 유형 | 건수 | 원인 |
|---|---|---|
| 브랜드 미추출 | 48 | 제품명만 언급하는 질의(`Lip Sleeping Mask ...`)에서 브랜드 링크 실패, 크래시 7문항 포함 |
| 대문자 subject 미조회 | 11 | 시드 온톨로지는 `LANEIGE -ownedByGroup-> AMOREPACIFIC`(대문자)인데 추출 브랜드는 소문자라 조회 대상에서 빠짐 |
| 12개 상한 truncation | ~10 | 선택 순서가 `relevant + product + competes[:3] + rest`여서 competesWith가 ownedBy·rankedIn을 밀어냄 |
| 브랜드 substring 오탐 | — | `share of shelf`의 `shelf`가 브랜드 `e.l.f.`로 매칭 (별칭 `elf`) |

### 1-e. 골드 kg_entities의 20%는 카테고리인데 지표가 세지 않았다

`gold.kg_entities` 518건 중 104건(93문항)이 카테고리 ID(lip_care, face_powder 등).
`_compute_entity_link_f1`은 brands·products·indicators만 합집합으로 써서 이 항목은
**구조적으로 매칭 불가**였다 — 추출기는 카테고리를 별도 필드로 정상 방출하고 있었다.

## 2. 수정

### 측정 인프라 (eval/)
1. `normalize_constraints()` 신설 — dict constraint를 `field:operator:value`로
   직렬화. 크래시 제거 (`eval/metrics/l1_query.py`, 회귀 테스트 2건).
2. entity 집합에 `extracted_categories` 포함 (1-e 근거).
3. `kg_edge_recall` / `kg_edge_precision` 신설, **게이트를 recall 기준으로 전환**
   (임계 0.5 동일). `kg_edge_f1`은 연속성을 위해 계속 보고하고, overall 점수
   공식은 v4.1과 동일하게 F1을 쓴다 — v4.1↔v5.0 비교 유효성을 위해서다.
   recall만 보면 "엣지 전량 방출"이 이득이므로 방출 상한 12개를 유지하고
   precision을 함께 보고해 남용을 감시한다.
4. 회귀 비교기: 베이스라인에 없는 신설 지표는 기본값 0.0으로 비교하지 않고 건너뛴다
   (신설 지표가 항상 "개선"으로 잡히는 오독 방지).

### 시스템 (src/rag/)
5. KG 엣지 조회를 브랜드 원형·소문자·대문자·title 4변형으로 확장 (1-d ownedBy).
6. 엣지 선택 순서를 `relevant → product → 정체성·지표(rest) → competes[:3]`로 바꾸고
   rest 내부도 `ownedBy > hasSoS > rankedIn > hasHHI > hasPosition` 순 정렬 + 중복 제거.
7. 브랜드 사전 매칭에 단어 경계 적용 (라틴 문자 키에 한정 — 한글은 조사가 붙으므로 제외).
8. KG 제품 타이틀 → 제품명 슬러그 인덱스로 **제품명에서 브랜드 역링크**.
   질의가 직접 지목한 제품은 랭크와 무관하게 엣지 방출.

### 기각한 변경 — 브랜드 미추출 시 LANEIGE 기본 주입
오프라인 시뮬레이션 결과 엣지 recall +0.034(0.618→0.652), hits +0.10이지만
**precision이 0.377→0.074로 붕괴**하고 문항당 방출 엣지가 7.8→11.5로 늘었다.
지표 이득의 실체가 "골드의 암묵적 LANEIGE 관례에 맞추기"이고 정의형 질문
("SoS란?")에 브랜드 KG 이웃을 통째로 주입하는 컨텍스트 오염이므로 채택하지 않았다.

## 4. 함께 처리한 시스템 정리 (P4)

- **kg_backup 경로 버그**: `Path(__file__).parent.parent.parent`가 모듈 이동 후
  `src/`를 가리켜 `src/data/knowledge_graph.json`을 찾고 있었다. `parents[3]`으로
  수정 — `python -m src.tools.utilities.kg_backup backup` 정상 동작(2,700 트리플).
- **v4 프롬프트 통합**: `ResponsePipeline.SYSTEM_PROMPT` 하드코딩을 `PromptRegistry`
  경유로 전환(`prompts.use_centralized_prompts` 플래그 준수, 실패 시 인라인 폴백).
- **RSS 복구**: 12개 피드 전수 실측(HTTP 상태 + 파싱 엔트리 수) 후
  korea_herald·cosmetics_business·premium_beauty_news를 동작하는 URL로 교체,
  410 Gone(cosmetics_design_asia/europe)·403 봇차단(byrdie/happi/beauty_packaging)은 제거.
  브라우저 UA로 본문을 받아 파싱하는 경로 추가. **7개 소스 중 5개에서 기사 수집 확인.**

## 6. 남은 과제

1. **L3 엣지 recall의 상한 0.54** — 골드 엣지 46%가 KG 부재. 골드를 고치는 대신
   KG 커버리지(경쟁사 산출 방식, 카테고리 확장)를 늘리거나, 골드 엣지를 별도
   "도메인 기대치" 세트로 분리하는 설계 논의가 필요하다.
2. **L2 지표의 구조적 취약성** (다음 사이클 P3 진단에서 확인): 160문항의 골드
   `doc_chunk_ids`가 **서로 다른 7개 청크**만 가리키고, 그중 119건(2개 청크)이
   `laneige_strategy_2026` 문서인데 실제 검색 적중은 2건뿐이다.
3. **RAG 코퍼스 침묵 누락** (사이클 5에서 처리): `DocumentRetriever`가 만드는 청크는
   2,242개인데 ChromaDB에는 271개만 색인돼 있다 — IR 분기보고서 3종 1,971청크가
   통째로 검색 불가 상태. 원인은 `if collection.count() == 0`으로 최초 1회만
   색인하던 조건. 증분 색인으로 수정했고 효과 측정은 다음 실행에서 한다.
