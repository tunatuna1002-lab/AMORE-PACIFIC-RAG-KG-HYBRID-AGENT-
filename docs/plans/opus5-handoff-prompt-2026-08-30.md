## 할 일
계획서의 작업 패키지를 P1(L3 엣지 재진단) → P2(L1 엔티티 커버리지) → P3(RAG 코퍼스 확충)
순으로 진행하고, P4(시스템 정리)는 P1~P3 사이 틈에 처리한다. 각 패키지는 계획서 3절의
사이클 루프(무비용 진단 → 수정 → 테스트 → 필요시 스모크 → 160문항 본실행 → compare →
baseline 저장 → 문서화 → 커밋 → push)를 따른다.

## 판단 원칙
- 사용자가 요청한 것을, 의도한 범위에서 완수하라. 애매함은 신중한 동료가 하듯 해석하고,
  해석에 따라 결과물이 실질적으로 달라질 때만 확인을 구하라. 더 나은 접근이 보이면 한 문장으로
  말하고 요청된 작업을 계속하라 — 조용히 범위를 좁히거나 넓히거나 변형하지 마라. 작업 전체를
  끝내라. 정말 끝낼 수 없는 부분이 있으면 나머지를 끝내고 무엇이 왜 남았는지 명시하라.
- 돈이 드는 실행(160문항 평가) 전에 반드시 v4.1 리포트 로컬 분석으로 원인을 수치로 확정하라.
  진단 없는 재실행은 금지다. 사이클당 본실행은 1~2회가 상한이다.
- 지표·골든셋·게이트를 결과가 좋아 보이도록 조정하지 마라. 구조 결함을 수치로 입증한 경우에만
  고치고, 근거를 docs/experiments/에 남겨라. 모든 개선 주장은 compare 출력이나 리포트 수치로
  뒷받침하라. 나빠진 지표도 그대로 보고하라 — 이 리포의 가치는 정직한 측정 기록이다.
- 평가 실행 조건은 계획서의 표준 명령을 그대로 써라. 특히 FF_AGENTS_USE_EXTERNAL_SIGNALS=false는
  Tavily 월 쿼터 보호용이니 바꾸지 마라. .env 값은 읽되 어디에도 출력·기록하지 마라.

## 프롬프트 설계 노트 (왜 이렇게 썼나)

Anthropic의 Opus 5 마이그레이션/프롬프팅 가이드에서 검증된 사항을 반영했다:

1. **전체 스펙 선불 제공 + 장기 자율 실행**: Opus 5는 "완전한 작업 명세를 주고 길게 돌리는"
   방식에서 최강. 그래서 세부를 프롬프트에 욱여넣지 않고 계획서(단일 소스)를 필독시키고
   프롬프트는 판단 원칙만 담았다.
2. **검증 지시 삭제**: Opus 5는 시키지 않아도 자기 작업을 검증하며, "검증하라/더블체크하라"
   지시는 과잉 검증(비용↑)을 유발한다고 명시돼 있다. 그래서 "검증해라" 대신 **완료 기준**
   (테스트 0 failed 등)만 제시했다.
3. **범위 이탈 방지 문구**: "조용히 범위를 좁히거나 넓히지 마라 / 전체를 끝내라" 블록은
   Anthropic이 테스트로 scope 이탈을 거의 0으로 줄였다고 보고한 권장 문구의 번안이다.
4. **서브에이전트 절제**: Opus 5는 전작과 반대로 서브에이전트를 과하게 쓰는 경향 — 권장
   절제 블록의 축약본을 포함했다.
5. **간결성 한 줄**: 기본 응답이 길어지는 경향에 대한 권장 완화 문구.
6. **공격적 명령형(CRITICAL/YOU MUST) 배제**: 4.6+ 모델은 프롬프트를 훨씬 충실히 따르므로
   과장 강조는 역효과 — 제약마다 이유(쿼터·비용·비교 유효성)를 붙이는 방식으로 작성했다.
7. **게이밍 금지 명시**: 이 작업의 특성상(평가 지표 개선) 가장 위험한 실패 모드가 지표
   게이밍이므로, 선례(구조 결함 입증 시에만 수정 + 문서화)를 규칙으로 명문화했다.
