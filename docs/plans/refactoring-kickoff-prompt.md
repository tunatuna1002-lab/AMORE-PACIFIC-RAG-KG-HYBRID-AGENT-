# Opus 5 리팩토링 세션 킥오프 프롬프트

> 새 Claude Code 세션(모델: Opus 5)에 아래 블록을 그대로 붙여넣기.
> 작성 근거: Opus 5 프롬프팅 가이드 — 과잉 검증 유발 지시 금지, 서브에이전트 남용 억제, 범위 규율, 완주 조항.

---

docs/plans/refactoring-plan-2026-08-31.md 를 읽고 그 계획을 Phase 0부터 6까지 순서대로 실행해줘. 계획서의 파일:라인은 어제 실측이니 수정 전 현재 위치를 재확인하고, 결정사항 D1~D4는 계획서의 권고안대로 확정한다 (코드 근거가 권고안과 정면 충돌하면 근거를 남기고 판단).

작업 규칙:
- 동작이 바뀌는 수정은 테스트를 먼저 추가하거나 갱신한 뒤 구현한다. Phase마다 관련 테스트를 돌리고, Phase 단위로 커밋한다 (커밋 메시지는 기존 컨벤션: `fix(scope): 한글 요약` + 본문).
- 전체 테스트(`.venv/bin/python -m pytest tests/ -q --no-cov`)는 Phase 0에서 기준선 1회, 전체 완료 후 1회만 돌린다.
- 골든셋 평가(비용 발생)는 Phase 4 완료 후 1회만: `.venv/bin/python -m eval.cli run --dataset eval/data/golden/laneige_golden_v2.jsonl` 후 최신 baseline과 compare. 회귀가 나오면 원인 파일만 되돌리고 기록한다.
- Phase 1은 지표 값 자체가 바뀌는 게 정상이다. 바뀐 값(HHI, SoS)의 before/after를 각 커밋 메시지에 기록해라.
- `src/rag/retrieval_strategy.py`와 그 테스트는 다른 세션이 작업 중이므로 건드리지 말고, 커밋할 때 파일 단위 스테이징으로 섞임을 방지해라.
- 계획서의 "명시적 비범위" 항목은 발견하더라도 손대지 말고 docs/dev/FUTURE_WORK.md에 한 줄 추가만 해라.

요청한 것을 요청한 범위대로 수행해라. 모호한 부분은 신중한 동료가 하듯 스스로 판단하되, 해석에 따라 결과물이 실질적으로 달라질 때만 질문해라. 계획이 잘못됐거나 더 나은 방법이 있다고 판단되면 한 문장으로 밝히고 요청받은 대로 계속 진행해라 — 조용히 범위를 좁히거나 넓히거나 변형하지 마라. 전체를 완료해라, 쉬운 부분만 하지 말고. 완전히 끝났을 때만 완료를 보고하고, 정말 끝낼 수 없는 항목이 있으면 나머지를 다 한 뒤 무엇이 왜 빠졌는지 명시해라.

서브에이전트 사용: 서브에이전트는 컨텍스트 재구축 비용이 크다. 정말 독립적이고 규모가 큰 병렬 탐색(예: 여러 모듈에 걸친 광역 조사)에만 드물게 써라. 파일 몇 개 읽기, 몇 군데 수정, 간단한 검색·확인은 직접 해라. 검증·리뷰 목적의 서브에이전트는 띄우지 마라.

작업 로그·문서를 쓸 때는 과제에 필요한 만큼만 써라 — 채움용 섹션, 중복 요약, 상투 문구로 문서를 늘리지 마라.

완료 후 최종 보고에는 Phase별 커밋 해시, 바뀐 지표 값 요약, 골든셋 compare 결과, 남긴 항목만 담아라.
